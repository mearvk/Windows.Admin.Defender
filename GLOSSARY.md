# Glossary

Definitions of the terms and tools used across Windows Admin Defender — the
kernel driver, the build/CI pipeline, and this repository's own concepts.
Grouped by area for quick reference.

## Windows driver concepts

- **WDK (Windows Driver Kit).** Microsoft's toolset (headers, libraries, tools,
  MSBuild integration) for building, testing, and packaging Windows drivers. It
  supplies the kernel headers (`ntddk.h`, `fltKernel.h`, `ntifs.h`) and import
  libraries (e.g. `fltMgr.lib`) that a driver compiles and links against.
- **EWDK (Enterprise WDK).** A self-contained ISO with the compiler, SDK, and
  WDK that runs from a command line via `LaunchBuildEnv`, without installing a
  Visual Studio extension. An alternative to the WDK MSI or the NuGet packages.
- **File-system minifilter.** A kernel driver that plugs into the Windows
  **Filter Manager** to observe or modify file-system operations (create, read,
  write, etc.) without being a full legacy filter driver. Windows Admin
  Defender's `.sys` is a minifilter.
- **Filter Manager (`fltMgr`).** The Windows kernel component that hosts
  minifilters and dispatches file-system callbacks to them. Minifilters link
  against `fltMgr.lib` and register with `FltRegisterFilter`.
- **Altitude.** A unique numeric value that determines a minifilter's position
  in the Filter Manager stack (load order relative to other filters). Assigned
  by Microsoft for production; the checked-in value is a development placeholder.
- **`DriverEntry`.** The entry point of a Windows kernel driver, analogous to
  `main` for a user-mode program. Here it registers the minifilter and starts
  filtering.
- **`FLT_REGISTRATION`.** The structure a minifilter passes to
  `FltRegisterFilter` describing its callbacks and options. Its members must be
  initialized in exact order and count (16 members for the current version) —
  supplying too many caused a `C2078: too many initializers` error during this
  work.
- **Pre-operation callback (preop).** A minifilter callback invoked before an
  I/O operation is processed (e.g. `WadPreCreate` runs before a file/directory
  create), allowing the filter to allow, block, or modify the request.
- **`.sys` file.** The compiled kernel driver binary (a PE image loaded into the
  kernel). Output of the WDK build — here, `WindowsAdminDefender.sys`.
- **`.inf` file.** A text installation manifest describing how Windows installs
  the driver: services, copy sections, registry keys, and (for minifilters) the
  instance/altitude. Installed via the Driver Store / PnPUtil.
- **`.cat` file (catalog).** A signed file containing hashes of the driver
  package; Windows uses it to verify package integrity and signing. Generated by
  `Inf2Cat` and signed as a separate packaging step.
- **Driver Store.** The trusted Windows repository of driver packages. Drivers
  are added/removed here (rather than copied ad hoc) via PnPUtil.
- **PnPUtil.** The Windows command-line tool for adding, installing, listing,
  and removing driver packages in the Driver Store
  (`pnputil /add-driver`, `/delete-driver`).
- **Code signing / test signing.** Windows requires kernel drivers to be
  cryptographically signed to load. **Test signing** uses a developer
  certificate for local testing; production requires an attested/EV-signed
  package. CI here compiles and links but does **not** sign (`SignMode=Off`).
- **Secure Boot, Code Integrity, Device Guard, UAC.** Windows security controls
  governing what code may run/load and with what privileges. Windows Admin
  Defender does not bypass any of them.

## WDK build tools

- **MSBuild.** Microsoft's build engine that drives `.vcxproj`/`.sln` projects.
  The WDK integrates with it, so `msbuild WindowsAdminDefender.vcxproj` builds
  the driver.
- **`.vcxproj`.** An MSBuild C/C++ project file (XML). Defines configurations,
  platforms, toolset, sources, and imports. This repo has one for the driver and
  one for the utility.
- **`.sln` (solution).** An MSBuild container grouping multiple projects and
  their configuration/platform mappings.
- **Platform toolset.** The compiler/linker set a project uses. The driver uses
  `WindowsKernelModeDriver10.0` (kernel-mode); the utility uses a normal
  user-mode toolset (`v143`).
- **`Directory.Build.props`.** An MSBuild file auto-imported for every project
  in its directory tree *before* each project. Used here to import the WDK/SDK
  NuGet package props so kernel headers resolve — Microsoft's recommended CI
  pattern.
- **Stampinf.** WDK tool (`stampinf.exe`) that stamps version/date information
  into the `.inf` during the build (the `StampInf` MSBuild task).
- **Inf2Cat.** WDK tool that generates the `.cat` catalog from the finalized
  driver package. A packaging step, separate from compilation.
- **InfVerif.** WDK tool that validates an `.inf` for correctness and Driver
  Isolation rules. Recent WDKs dropped its 32-bit DLL, so it is disabled in CI.
- **ApiValidator.** WDK tool that checks a driver only uses "universal" (broadly
  supported) kernel APIs. A post-build validation step, disabled in CI here.

## NuGet / dependency terms

- **NuGet.** The .NET/Windows package manager. Used here to acquire the WDK/SDK
  as packages (rather than a machine-wide install) so a hosted CI runner can
  build the driver.
- **`Microsoft.Windows.WDK.x64` / `Microsoft.Windows.SDK.CPP`.** The official
  NuGet packages providing the WDK and Windows SDK headers/libraries/tools for
  C++ driver builds. Note: the WDK package versions its patch number
  independently from the SDK, so they can differ.
- **`packages.config`.** A NuGet file listing packages and pinned versions to
  restore. Restored via `nuget restore ... -PackagesDirectory ...`.
- **`nuget restore`.** Downloads the packages listed in `packages.config` into a
  local `packages/` directory before the build.

## CI / GitHub Actions terms

- **GitHub Actions.** GitHub's built-in CI/CD system that runs workflows on
  hosted machines in response to events (push, pull request, manual dispatch).
- **Workflow.** A YAML file under `.github/workflows/` defining jobs and steps.
  Here, `build.yml` compiles the driver and utility on Windows.
- **Runner.** The machine executing a job. `windows-latest` is GitHub's hosted
  Windows image (includes Visual Studio and MSBuild; the WDK is added via NuGet).
- **Job / step.** A job is a set of steps run on one runner; a step is a single
  command or action. A job's overall `conclusion` (`success`/`failure`) reflects
  its steps.
- **Artifact.** Files uploaded from a workflow run for later download. Here the
  build outputs (`WindowsAdminDefender.sys`, `driver-defender.exe`, `.inf`) are
  uploaded as `windows-admin-defender-x64-Release`.
- **`.gitattributes` / line-ending normalization.** Git configuration that pins
  file line endings (LF) across platforms. Needed here so the checked-out bytes
  on a Windows runner match the SHA-256 digests in the verification manifest
  (a Windows checkout would otherwise convert LF→CRLF and change the hashes).

## Windows Admin Defender concepts

- **Directory-lock policy.** The driver's runtime behavior: for protected roots,
  normal file opens/reads remain allowed, but direct **directory-handle** opens
  are denied — blocking directory enumeration, wholesale copy, delete, and
  rename while keeping ordinary file I/O working.
- **Protected roots / protected folders.** The system directories the minifilter
  guards (e.g. `System32`, `SysWOW64`, `WinSxS`, `Program Files`, `ProgramData`).
  Policy source: `digital/lists/PROTECTED_FOLDERS.md`.
- **Protected store (stored-protected mode).** A local, MySQL-like object store
  keeping reference/vault copies of protected system files, deduplicated by
  SHA-256, with a relational-style catalog. It is a reference copy, never a
  replacement for the live Windows filesystem. See `digital/PROTECTED_STORE.md`.
- **Verification gate.** The fail-closed SHA-256 check (`build/verify.ps1`) run
  before build/execution/diagnostics: every protected file's bytes are hashed
  and compared to the manifest; any mismatch, missing file, unsafe path, or
  malformed digest stops the pipeline. See `updates/VERIFY-BEFORE-BUILD.md`.
- **Update manifest.** The JSON file (`updates/UPDATE-MANIFEST.json`) listing
  each protected file with its expected SHA-256 digest, consumed by the
  verification gate. Regenerate with `build/generate-manifest.ps1` when a listed
  file changes.
- **Fail closed.** A safety posture where, on any error or ambiguity, the system
  stops rather than proceeding. The verification gate fails closed.
- **`driver-defender` (administrator utility).** The user-mode console tool
  (`driver-defender.exe`) that wraps supported Windows admin commands (load,
  install/add, remove, status, policy, etc.) via `sc.exe` and PnPUtil.
- **SHA-256.** A cryptographic hash used for integrity verification and object
  identity in the protected store. Proves a file's bytes are unchanged; it does
  not by itself establish who published the file (that needs signing/Authenticode).
